# ADR-006：软删除 + 回收站三级协议 + 永久删除 GC

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

业务对象（客户、保单、理赔、文档、活动、任务）涉及高价值或敏感数据，误删代价高。需求要求删除可逆，并有明确的恢复路径。

参考分析的结论：

- Immich（§1.8）：`trash.enabled=true, days=30`，软删除后 30 天物理清理。
- Paperless-ngx（§6.5）：`SoftDeleteModel` 软删除，物理文件移入回收站目录，定时任务按延迟时间硬删并清理审计日志；审计用中间件记录。

Keji 的情况比两者多一层复杂性：一份文件对象会同时关联客户、相册、工作事件、保单、理赔材料（reference-analysis §6.7 的结构分歧点）。永久删除必须保证 DB 记录、关联、原文件、缩略图、审计的一致，否则会留下孤儿文件或失效外键。

另一个约束来自 ADR-013：演示数据标记 `demo-` 前缀，重置命令需要能识别并清理演示数据，删除协议要与之兼容。

## Decision

采用三级删除协议：

1. 普通删除：业务对象标记 `is_deleted=True`、`deleted_at` 写入，对象从正常视图隐藏，进入回收站；关联的文件对象也进入软删除（但物理文件不动）。
2. 回收站：回收站视图可恢复（`is_deleted=False`、`deleted_at=NULL`）；可对整个删除集合或单条执行。
3. 管理员永久删除：一致性流程，必须按顺序处理：
   - 删除/解除数据库记录与外键关联（含 M2M 中间行）；
   - 将原文件与缩略图移入 `trash/` 目录（由存储层完成，ADR-002）；
   - 写入审计日志（AuditLog），并明确**审计日志本身不随业务对象删除**；
   - 之后由 GC 命令真正物理清理。

配套机制：

- 提供 `purge_trash` 管理命令作为 GC：周期性扫描回收站中超过保留期（默认 30 天，可配置）的对象，执行物理清理，要求幂等、可重入、有日志。
- 文档等文件对象在回收站中不再参与去重候选，避免「回收站中的重复」被误判（参考 Paperless §6.2 对回收站重复的区分）。
- 恢复与永久删除操作本身都记审计。
- 永久删除为高危操作：仅管理员可执行，需二次确认页面。

## Consequences

正面：

- 误删可恢复，恢复路径明确。
- 审计日志独立于业务对象生命周期，历史不可被删除者抹掉。
- 物理清理集中在一个 GC 命令，便于测试与演练。

负面：

- 所有查询必须统一过滤 `is_deleted`，容易遗漏，需要基础 manager 与测试兜底。
- 永久删除的一致性路径复杂（记录、关联、两处存储键、审计），是回归测试重点（见 docs/testing.md §26）。
- 回收站数据仍占磁盘，保留期越长占用越多。

## 实现要点

- 为所有软删除模型提供统一 QuerySet manager：正常查询自动排除 `is_deleted`，回收站查询走专用 manager。
- GC 命令必须可重入：上次中断后再次运行不重复处理、不报错。
- 恢复时校验关联完整性：被恢复对象的关联对象仍存在且未永久删除，否则恢复为孤儿并提示。
