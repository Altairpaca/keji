# ADR-007：HTMX + Alpine.js + 服务端模板

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

界面交互需求以表单、列表、局部刷新为主：客户 CRUD、时间线追加、批量上传进度、回收站操作、筛选排序。这类场景用传统多页应用配合局部片段替换即可良好覆盖。

评估 SPA 路线（React/Vue）时，参考分析 §5 给出了明确倾向：MicroPyramid 与 DjangoCRM 研究均以「拒绝 DRF + React 前端，与 HTMX/SSR 栈不符」收尾；Twenty 的 React/GraphQL 前端属于重型方案，仅借鉴其保存视图建模，不复制前端。

SPA 的代价与 ADR-001 一致：构建链、前后端两套代码、接口层维护。而当前团队规模下，服务端模板的成本最低、可维护性最好。

另一个现实约束：手机端是主要使用场景（ADR-009），弱网环境下首屏必须尽快可交互。服务端模板首屏直出 HTML，比 SPA 的白屏等待更适合这种网络环境。

## Decision

- 页面渲染采用 Django 模板服务端渲染，首屏内容直接输出 HTML。
- 局部交互（列表筛选、分页、表单提交、时间线追加）用 HTMX：通过 `hx-get`/`hx-post` 返回 HTML 片段替换目标区域，不强刷整页。
- 客户端状态与轻量交互（开关、下拉、弹层、拖拽排序的小范围状态）用 Alpine.js 的 `x-data` 管理，不引入完整状态管理库。
- 不引入 SPA 框架（React/Vue/Svelte），不写独立的 REST/GraphQL 前端。
- JSON 接口只在确需程序化数据交换处提供（关系图数据，见 ADR-010；上传接口按 ADR-009 处理）。
- 服务端仍保持「视图薄、逻辑进服务层」的分层（AGENTS.md），HTMX 片段视图与页面视图共用服务函数。

## Consequences

正面：

- 单仓库单技术栈，后端开发者可独立完成全栈功能。
- 无 Node 构建链，与 ADR-008 的 Tailwind 产物策略一致，生产部署轻。
- 首屏直出，弱网下可交互时间短，契合手机端场景。
- 渐进增强：JS 不可用时大部分表单仍可提交。

负面：

- 复杂实时交互（画布拖拽、复杂动画、离线编辑）做起来别扭，超出范围时需单独评估。
- HTMX 调试依赖浏览器网络面板，需要建立局部片段的可测试性（docs/testing.md 的页面渲染测试覆盖）。
- 交互逻辑分散在模板属性与 Alpine 表达式里，需约定书写规范避免失控。

## 实现要点

- 模板按「页面模板 + 局部片段模板」组织，片段模板可直接被 HTMX 渲染并可被页面模板 include 复用。
- HTMX 请求的响应头处理（重定向、消息闪现）统一封装，避免每处手写。
- Alpine 状态对象限制单文件内，禁止全局共享可变状态。
- 片段模板的 URL 命名空间与页面模板一致，便于测试直接按 name 解析。
- 大量 HTMX 片段复用同一服务函数的，在服务层做参数化，避免视图重复。
- 上传、关系图等 JS 较重页面按需加载脚本，不整站打包。

## 被否决的备选

- React/Vue SPA：参考分析 §5 明确拒绝，构建链与团队规模不符，弱网首屏白屏。
- 纯 MPA（无 HTMX，全页刷新）：手机弱网下每次操作整页刷新，体验差；HTMX 增量成本很低。
- Alpine 换完整状态管理库（Redux 之类）：对当前交互规模过重，与「轻量前端状态」的定位矛盾。
