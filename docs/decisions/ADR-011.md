# ADR-011：备份 = pg_dump(custom) + 媒体卷 tar + manifest + 保留策略 + 还原演练

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

系统存两类数据：PostgreSQL 中的业务数据（含元数据、存储键、审计日志）与存储层中的原始文件、缩略图（ADR-002）。只备份数据库会丢文件，只备份文件会丢结构与权限。两者必须一起备份才可恢复。

参考分析 §6.6 记录了 Paperless-ngx 的双轨制：管理命令导出文件加 manifest.json（含元数据/标签/审计），同时官方要求另做 PostgreSQL 备份，因为导出器不含运行时数据。

本系统没有 Paperless 那样的 exporter 全量机制，但参考其思路：文件清单必须带校验和，用于恢复后核对完整性。参考分析同时明确「第一版不做增量与加密，但保留 manifest + checksum」，本决策沿用该边界。

备份是部署者的责任，也是合规底线的一部分（docs/security.md 隐私法律边界）。一个没有演练过的备份方案等于没有备份，因为首次真正需要恢复时才发现坏档是最坏的结果。

## Decision

备份方案由五部分构成：

1. 数据库：`pg_dump --format=custom` 输出数据库备份文件（custom 格式支持选择性恢复）。
2. 媒体卷：`tar` 打包 `originals/`、`thumbnails/` 目录（ADR-002 的存储根）。
3. manifest.json：备份批次清单，记录备份时间、pg_dump 文件与媒体 tar 的文件名、各文件 SHA-256 checksum、版本号、保留元信息。
4. 保留策略：默认保留最近 N 份（如 14 份或 30 天），超期自动清理，策略可配置。
5. restore 脚本与演练：提供 `restore.sh` 把备份批次还原到空库与空媒体目录，执行校验和核对；还原演练纳入发布与变更流程，定期执行（如每次大版本发布前）。

配套约定：

- 备份通过管理命令或 cron 触发，产出到备份目录（docker 卷挂载或独立目录）。
- 备份期间不依赖系统停机：pg_dump custom 在线执行，媒体 tar 对静态目录打包。
- 还原演练的步骤与结果记录成文档，作为部署者责任的落地（docs/security.md）。
- 明确 Tailscale 等内网通道不是备份替代，只是访问手段（docs/security.md 隐私法律边界）。

## Consequences

正面：

- 数据库与文件同时可恢复，恢复路径可被演练验证。
- manifest 加 checksum 能在还原后确认无静默损坏。
- 保留策略避免备份无限增长。

负面：

- 备份脚本与演练需要维护成本，未演练时是最不可靠的一环。
- 备份目录本身需要额外磁盘空间。
- 还原演练需要临时环境，不能直接覆盖生产。

## 实现要点

- 备份命令输出唯一批次号，manifest 文件名带批次号，便于回滚定位。
- 还原演练用备份批次在空库上执行并断言关键记录数（客户数、文件数、审计条数）。
- 备份失败要有告警渠道（日志、通知脚本），静默失败等于没有备份。

## 被否决的备选

- 只备份数据库：丢全部媒体文件，系统不可完整恢复。
- 只备份媒体卷：丢结构与权限，恢复出来是一堆无主文件。
- 备份不带 checksum：无法发现静默损坏，恢复后才发现坏档。
- 有备份无演练：备份成为「心理安慰」，首次真恢复时才发现流程失效。
