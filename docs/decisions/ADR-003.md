# ADR-003：搜索用 PostgreSQL pg_trgm + GIN 索引

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

需求包含跨模型的全局搜索：客户名、保单号、理赔号、沟通内容等。评估了三条路线：

1. PostgreSQL 内置 FTS（`SearchVector`/`SearchRank`）。参考分析 §3 明确结论：**默认分词器对中文失效**。`to_tsvector('中文文本')` 会把整串当一个 token，`simple`/`english` 分词器没有中文词边界，裸用 FTS 搜中文基本无效。要真正可用必须自装 zhparser 或 pg_jieba 扩展，而扩展编译与升级依赖属于自托管环境的额外负担。
2. Elasticsearch。功能强但引入独立服务：额外运维、内存开销、索引同步、与 ADR-001 单容器部署风格冲突。对当前规模属于过度投入。
3. pg_trgm 扩展。以三字符组（trigram）做子串与模糊匹配，Django 内置 `TrigramSimilarity`、`TrigramWordSimilarity` 与 `__trigram_similar` lookup，配合 `GIN (col gin_trgm_ops)` 索引即可。对「张三」「张小明」这类中文模糊匹配有效。

参考分析 §3 的最终建议即本决策的依据：短字段用 pg_trgm，长文本若要求相关度排序再评估 zhparser，不要裸用默认 FTS 搜中文。

## Decision

采用 pg_trgm + GIN 作为搜索的默认方案：

- 客户、保单、理赔等短字段统一建 `GIN (gin_trgm_ops)` 索引。
- 搜索实现走 Django ORM 的 `TrigramSimilarity`/`TrigramWordSimilarity`，按相似度排序。
- 跨模型合并搜索按 reference-analysis §3 的思路：各模型输出统一的 `(pk, type, rank)` 列再合并排序，二次按 type 取实例。
- 长文本（沟通记录正文）本阶段同样先用 pg_trgm 覆盖子串搜索；若后续明确需要相关度排序，再评估安装 zhparser 扩展，作为增量演进。
- 明确不引入 Elasticsearch。

## Consequences

正面：

- 中文子串与模糊搜索开箱即用，不引入额外服务，符合自托管与单容器部署（ADR-001）。
- 索引与查询都由 Django 内置支持，无自定义扩展编译依赖。
- 运维面小：一个数据库实例即可。

负面：

- 不支持语义搜索、同义词扩展；「搜索质量」上限低于 FTS 或 ES。
- trigram 索引对超长文本字段效果有限，长文本搜索需在数据量增长后重新评估。
- 若未来选 zhparser，需在迁移中加扩展并重建索引，属破坏性变更。

## 实现要点

- 搜索表单做输入长度下限与上限校验，防全表 trigram 扫描。
- 搜索结果统一分页，跨模型合并结果按页截断（参考分析 §3 的 union 分页限制）。
- 为每个参与搜索的字段写单元测试，断言中文子串命中与排序（docs/testing.md 全局搜索范围）。
- 相似度阈值按字段区分：短字段（客户名、保单号）阈值放宽，长文本字段收紧，避免噪声结果。
- 索引随迁移创建，字段变更时同步更新迁移，禁止手工建索引。
- 搜索端点对未认证请求一律返回 401/403，不泄露是否存在数据。

## 被否决的备选

- 裸用默认 FTS 搜中文：参考分析 §3 的直接结论，默认分词器对中文失效，整串当一个 token，已排除。
- 第一版就装 zhparser 扩展：需要编译安装 PG 扩展，自托管环境的依赖与升级负担重，作为增量演进而非首发。
- 引入 Elasticsearch：独立服务与 ADR-001 单容器部署冲突，运维与内存成本对当前规模是浪费。
