# ADR-009：手机多选上传用原生 input，重试优先，不做完全离线

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

手机端（主要使用场景）需要从相册多选照片批量上传到客户/相册/工作事件，且要能在弱网下尽量成功。

评估了原生插件路线（Cordova/Capacitor 拍照与相册插件）：引入插件意味着维护原生层、版本对齐、构建复杂度，与 ADR-001 的单体部署与 ADR-007 的纯 Web 栈冲突。应用商店审核与签名流程也会拖慢发布节奏，对自托管工具不值。

参考分析 §1.7 记录 Immich 的实测策略：移动端前台默认 3 并发 worker 池上传，后台 isolate 串行。这套并发策略直接可借鉴。

上传的取舍核心是「数据一致性优先还是完全离线优先」。完全离线（本地队列、离线编辑、后台同步）意味着客户端状态与服务器状态可能冲突，典型后果是旧数据覆盖新数据、重复上传、版本漂移。对当前规模（个人代理人管理自己的客户资料）收益低而成本高。

## Decision

- 上传入口使用原生 `<input type="file" multiple accept="image/*" capture>`，不引入任何原生插件。
- 前端拿到 FileList 后分批上传：默认 3 并发 worker（对齐 Immich 前台策略），服务端逐个校验与入库。
- 上传失败自动重试：临时网络错误指数退避重试（如 3 次），业务性拒绝（类型不对、超大小、重复）不重试，直接提示。
- 每个文件独立状态（待传/传输中/成功/失败），失败项可单点重传，全部成功后提示完成。
- 服务端保留上传接口为普通表单或 JSON 端点，配合 Django CSRF 保护（docs/security.md）。
- 明确不做完全离线：不做本地持久化上传队列、不做离线编辑。断网时提示用户，不假装同步成功，避免旧数据覆盖新数据。
- 上传前做客户端预检（大小、类型），服务端仍强制终检（安全策略见 docs/security.md）。

## Consequences

正面：

- 无原生依赖，手机浏览器直接可用，发布与升级只靠 Web 更新。
- 重试与并发策略对齐已验证的 Immich 做法，弱网体验可控。
- 数据一致性始终以服务器为准，不会出现客户端旧状态覆盖新数据。

负面：

- 完全离线场景不支持，离线期间产生的内容无法排队，需用户手动处理。
- 大批量上传（上百张）在极弱网下耗时较长，进度体验依赖前端实现质量。
- 多选受浏览器对 `accept` 的限制，个别机型相册筛选可能不完美。

## 实现要点

- 上传进度用 Alpine.js 管理（ADR-007），每文件状态与重试按钮在模板中可渲染。
- 服务端对同一文件并发上传去重：以 SHA-256 checksum 为唯一键，重复请求返回既有记录。
- 上传超时与重试上限写入配置，避免弱网下无限重试拖垮连接。
- 上传完成后的关联动作（挂到客户/相册/事件）在一个事务内完成，避免「文件进了、关联没挂」的半截状态。
- 重复文件直接复用既有存储键与记录，不重新生成缩略图。
- 上传接口加请求体大小上限与连接超时，防止超大文件拖垮 worker。

## 被否决的备选

- Cordova/Capacitor 原生相册插件：原生层维护、版本对齐、商店审核成本，与 ADR-001/007 的纯 Web 栈冲突。
- 完全离线队列（IndexedDB 本地队列加后台同步）：双副本一致性风险，旧数据覆盖新数据，与「数据一致性优先」原则矛盾。
- 单文件串行上传：弱网大批量场景太慢，Immich 已实测 3 并发前台更优。
