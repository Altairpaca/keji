# ADR-002：存储抽象层（StorageBackend 接口 + LocalDisk 实现，预留 S3）

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

系统要保存两类文件：用户上传的原始文件（照片、扫描件、病历、理赔材料等）与系统派生的缩略图。

参考分析的两个结论直接约束本决策：

- Immich（reference-analysis §1.2）：原图与派生图分离存储，缩略图可重建，原图只写不读；缩略图管线单次解码多尺寸复用（§1.3）。
- Paperless-ngx（reference-analysis §6.1）：数据库不存路径模板，只存唯一存储键与原始文件名；原图、缩略图、回收站分目录。

另外，部署者可能自托管在单机磁盘，也可能未来迁移到 S3 兼容的对象存储。希望应用代码不感知这种差异，切换存储时不需要改业务代码。同时必须遵守 ADR-005：存储键使用 UUID，绝不用客户姓名或原始文件名作路径。

本系统与 Paperless 的结构差异（reference-analysis §6.7）也影响存储设计：一份文件对象要关联多个实体（客户、相册、工作事件、保单、理赔材料），因此 checksum 与存储键挂在文件实体上，关联走 M2M，服务器只存一份原始文件。

## Decision

引入一个薄的存储抽象层：

- 定义 `StorageBackend` 接口，提供保存、读取、删除、探测存在性等最小操作，统一以「存储键」为参数，不暴露文件系统路径。
- 第一版实现 `LocalDiskBackend`，文件写到 `MEDIA_ROOT` 下按用途分离的目录：`originals/`、`thumbnails/`、`trash/`。
- 接口预留 `S3Backend` 实现位（通过配置切换），但不在本阶段编码。
- 存储键统一为 UUID，带两级分片前缀（形如 `ab/cd/<uuid>`），避免单目录文件过多。
- 数据库不存二进制内容，只存：存储键、原始文件名、SHA-256 checksum、MIME 类型、像素尺寸、拍摄时间等元数据。
- 原始文件与缩略图使用不同存储键、不同目录；缩略图视为可重建的派生物，重建管线对齐参考分析 §1.3（一次解码多尺寸复用）。
- 文件校验（MIME、大小、魔数、扩展名）在写入路径强制执行，策略见 docs/security.md。
- 上传前按 SHA-256 checksum 查重，跳过重复文件（参考 Paperless §6.2 与 Immich §1.6）。

## Consequences

正面：

- 应用代码不关心底层是磁盘还是对象存储，迁移成本低。
- 缩略图损坏或丢失可重建，不丢原始数据。
- checksum 入库前查重，避免重复入库。
- 路径穿越等风险被收敛在存储层实现内部，单一责任点。

负面：

- 多一层接口抽象，需要配套单元测试。
- S3Backend 本阶段不实现，真迁移时仍需开发与回归测试。
- 原图与缩略图分离，删除路径必须同时处理两个存储键（见 ADR-006 的一致性删除）。

## 实现要点

- 接口方法的参数与返回值禁止包含绝对路径；错误以自定义异常表达，不抛裸 `OSError` 细节。
- `LocalDiskBackend` 内部必须做路径规范化与 `..` 拒绝（docs/security.md 路径穿越防护）。
- 缩略图生成失败的降级路径：原图可看、缩略图标记为空，不得阻断上传。

## 被否决的备选

- 直接用 Django 默认 FileField 与默认存储：字段类型把存储路径耦合进模型，违反「DB 不存路径、只存存储键」原则，删除时缺少统一清理点。
- 二进制直接存 PostgreSQL（bytea）：数据量大时拖垮数据库、备份体积暴涨，缩略图无法独立重建。
- 不设接口、直接面向磁盘写代码：切换对象存储时全代码库散落路径拼接，且路径穿越防护无处收敛。
