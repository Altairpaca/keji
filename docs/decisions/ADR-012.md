# ADR-012：角色模型 = 管理员 / 普通用户 + 11 权限位，服务端验证

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

系统需要区分谁能做管理操作（永久删除、审计查看、系统设置）与谁能做日常操作（查看客户、上传文件）。参考分析 §6.4 中 Paperless 的 owner 加对象权限模型对 Keji 过重，ADR-004 已决定手写权限位方案。

角色问题与权限位问题是一体的：角色是权限位的分组与命名，权限位是服务端校验的最小单位。为了避免「角色门禁只存在于 UI」的漏洞，必须明确角色只在服务端落地，模板层的隐藏纯粹是展示性优化。

从部署形态看，自托管场景通常只有两种人：系统主人（管理员）与授权协作者（普通用户）。两类的边界足够清晰，不需要第三类角色去模拟。这也是不引入通用 RBAC 框架（如 django-guardian）的运营侧理由：多角色矩阵是为组织级系统准备的，这里用不上。

## Decision

- 角色共两类：
  - 管理员：`is_superuser=True`，拥有全部 11 个权限位（服务端由 `requires_permission` 直接放行），可执行仅管理员的动作（审计日志查看、系统设置、永久删除、用户管理）。
  - 普通用户：`is_superuser=False`，按 11 个权限位字段逐项授权，默认值见 docs/security.md 权限矩阵。
- 权限校验一律在服务端：视图函数挂 `requires_permission`（ADR-004），模板只做入口隐藏。
- 没有 UI-only 门禁：任何「只有管理员能看到」的按钮或链接，其对应视图或接口必然存在服务端 403 校验。
- 管理员创建/停用普通用户是管理动作，仅管理员可执行；普通用户不能自提权限。
- 第一版不做多角色扩展（如只读运营角色），若未来需要，在现有权限位基础上增加角色映射即可，不改变校验机制。

## Consequences

正面：

- 安全模型简单：两个角色、11 个开关、一个装饰器，容易审计与测试。
- 管理员覆盖一切，避免「管理员也被某权限位卡住」的配置事故。
- 无 UI-only 门禁，越权路径在服务端被阻断。

负面：

- 粒度为「功能域级」而非「对象级」，无法表达「只允许看某几个客户」。
- 角色概念是隐式约定（is_superuser 加权限位），缺少独立的角色表，需要文档与测试把约定固化。

## 实现要点

- 权限位的默认值集中在 accounts 模型迁移中定义，普通用户创建入口统一引用默认值。
- 用户管理页面提供权限位开关与「设为管理员」两个动作，改动立即生效（不依赖缓存）。
- 安全测试针对每一类角色各建 fixture，见 docs/testing.md 权限拒绝范围。
- 普通用户的默认权限位对应「日常操作可用的最小集合」，新用户开箱即用常见操作。
- 权限位变更写入审计日志，便于追溯谁给谁开了什么权限。
- 视图权限清单从装饰器声明自动生成，与 security.md 矩阵对照校验。
- 停用用户立即断开会话：修改 `is_active` 后下次请求即被拦截。
- 管理员对权限位的修改不需要重启服务，字段级即时生效。
- 普通用户视图上下文注入权限标记，模板据此渲染入口，来源仍是服务端声明。

## 被否决的备选

- 通用 RBAC 框架（django-guardian 等）：角色矩阵与对象授权为组织级系统准备，Keji 自托管场景只有「主人与协作者」两类人，用不上。
- 三档以上角色（如加只读运营角色）：当前没有可被第三类角色承接的明确职责，先不做，需要时在权限位之上加映射即可。
- UI-only 角色切换：不落服务端校验，等于没有安全模型，违反本决策核心。
