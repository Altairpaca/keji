# ADR-004：手写权限位 + requires_permission 装饰器（服务端强制）

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

系统有管理员与普通用户两类角色（见 ADR-012），需要按功能域控制谁能看客户、谁能改保单、谁能下载文件等。

参考分析 §6.4 记录了 Paperless-ngx 用 django-guardian 做对象级权限，并有 owner 快捷通道。但 Keji 是单管理员加少量普通用户的小规模自托管系统，对象级权限（每一条记录单独授权）的需求并不存在：普通用户要么整体开放，要么由管理员逐个开关功能权限。

引入 django-guardian 会带来：额外依赖、权限表膨胀、每对象权限判断的开销、以及把简单模型复杂化的风险。当前规模不值得。

同时，权限绝不能做成「只在 UI 上隐藏按钮」的装饰性门禁。UI 隐藏只解决观感，服务端必须强制校验，否则绕过前端即可越权。参考分析 §5.4 的 DjangoCRM 研究也提醒：逻辑堆在 model 层会导致权限判断散落各处，必须把校验收敛到统一装饰器。

## Decision

采用手写权限位方案：

- 在 `accounts.User` 上挂 11 个布尔权限位字段（`perm_customer_view`、`perm_customer_manage`、`perm_policy_view`、`perm_policy_manage`、`perm_claim_view`、`perm_claim_manage`、`perm_document_view`、`perm_document_manage`、`perm_document_download_export`、`perm_activity_view`、`perm_activity_manage`），全部定义与默认值写入 docs/security.md 的权限矩阵。
- 提供 `requires_permission('perm_x')` 装饰器用于视图函数，统一封装：未认证重定向登录，已认证但无权限返回 403。所有敏感视图必须挂装饰器。
- `is_superuser`（管理员）视为拥有全部权限，装饰器对其直接放行。
- 模板层只做展示性隐藏（隐藏无权限的操作入口），**真正校验一律在服务端**。
- 不引入 django-guardian；不实现对象级权限，但保留 owner 归属字段（参考 Paperless 结构）以备未来演进。

## Consequences

正面：

- 权限模型一眼可读：11 个字段，无需查权限表。
- 服务端强制校验，无法靠绕过前端越权。
- 不引入额外依赖，测试简单（直接断言 403 即可）。

负面：

- 对象级权限缺失：一旦出现「只允许某用户看某几个客户」的需求，需要重新评估方案。
- 新增权限位需要同时改：模型字段、装饰器注册、迁移、security.md 矩阵、测试。维护纪律要求高。

## 实现要点

- 装饰器同时处理匿名用户（重定向登录）与已认证无权限（403）两类分支，都要有测试。
- 列表视图的过滤与服务端校验一致，避免「列表可见、详情 403」不一致。
- 每个权限位对应一个 403 断言测试，见 docs/testing.md 权限拒绝范围。
- 装饰器校验放视图入口而非中间件：视图明确声明依赖，测试可见、权限清单可生成。
- 权限位字段在 User 上以 `perm_` 前缀命名，管理后台按组展示，防止误配。
- 装饰器支持参数化的权限名，保证视图可声明多个权限位（任一通过即可）。
- 装饰器顺序位于 CSRF 与登录之后，避免未认证先查权限表。

## 被否决的备选

- django-guardian 对象级权限：参考分析 §6.4 中 Paperless 采用它，但 Keji 无「每条记录单独授权」的场景，引入后权限表膨胀、每对象判断有开销。
- Django 自带 permissions framework（auth.Permission）：权限按模型粒度注册，无法表达「下载/导出」这类跨模型能力；且普通用户的权限分配要走 group/permission 表，绕开布尔字段的直接性。
- 只做模板层隐藏、服务端不校验：等于没有权限，绕过前端即越权，直接违反本决策的前提。
