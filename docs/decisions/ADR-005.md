# ADR-005：所有领域模型 UUID 主键 + UUID 存储键

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

选择主键类型时有三类隐患要避免：

1. 自增整数主键会泄露业务规模：从 URL 里的 `id=12345` 就能推断出系统有多少客户、多少保单。对存储敏感个人信息的系统，这是不必要的暴露面。
2. 把客户姓名、身份证号、保单号等可识别信息用作文件路径或文件名：一旦路径泄漏到日志、错误页或 URL，隐私数据随之暴露；且改名、重名会破坏文件引用。
3. 备份与多实例合并场景：自增主键在跨库合并时容易冲突，UUID 天然无冲突。

参考分析的两点直接相关：

- Paperless-ngx（§6.1）数据库只存唯一存储键与原始文件名，不存路径模板；原始文件名单独保留。
- Immich（§1.2）原图与派生图均以资产 UUID 派生命名。

此外，全局搜索（ADR-003）与审计（audit app）都需要稳定的对象引用：UUID 保证跨软删除、跨备份恢复周期引用不漂移。

## Decision

- 所有领域模型（accounts、customers、activities、documents、policies、claims、tasks 等）主键一律使用 `UUIDField(primary_key=True)`，默认 `uuid4` 生成。
- 文件存储键同样使用 UUID（带分片前缀），绝不用客户姓名、身份证号、保单号、原始文件名作为存储键或路径。
- 原始文件名仅作为元数据字段保留在数据库里，只用于展示与下载时还原（配合 Content-Disposition，见 docs/security.md）。
- 展示给用户的 URL 一律基于 UUID，不暴露自增序号。
- 关联表（M2M 中间表、CustomerRelation 等）主键同样 UUID，外键字段保持类型一致。
- 时间戳字段（created_at、updated_at）作为排序与审计依据，UUID 不做顺序语义。

## Consequences

正面：

- 不可枚举：无法通过遍历 ID 猜测他人记录，配合权限校验降低越权面。
- 无真实 PII 进入文件路径，泄漏面小。
- 备份恢复、跨实例合并无主键冲突（ADR-011 恢复演练更稳）。
- 与存储层（ADR-002）的接口签名统一，均为 UUID 键。

负面：

- UUID 比整数占用更多空间，索引略大；对当前数据量（千级到万级记录）影响可忽略。
- UUID 不带可读顺序，调试时不如自增直观，需要借助 created_at 排序。

## 实现要点

- 自定义基础模型（`TimeStampedModel` 之类）统一提供 UUID 主键与时间戳，各 app 模型继承，避免每处手写。
- 所有 URL 参数名统一用 `<uuid:pk>`，路由层约束非法 UUID 直接 404 而非 500。
- 迁移中旧数据转换（若从自增迁移）需要一次性脚本，属于破坏性操作，仅在有真实数据时评估。

## 被否决的备选

- 自增整数主键：泄露业务规模，跨库合并冲突，已被本决策排除。
- 客户姓名、身份证号或保单号作文件路径：PII 进路径，日志与错误页都可能泄漏；改名重名破坏引用。
- 用原始文件名做存储键：重名冲突、含非法字符、可被猜测，与安全目标相悖。
