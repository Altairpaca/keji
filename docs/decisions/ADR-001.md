# ADR-001：模块化单体架构（非微服务、非前后端分离）

> 日期：2026-08-06

## Status

已接受（Accepted）

## Context

客迹 Keji 是面向小团队自托管的客户关系与文档管理工具，预期规模为单管理员加少量普通用户。功能域包含客户、保单、理赔、文档照片、活动任务、时间线等。

需求分析时出现过两种诱惑：把前端拆成独立 SPA，或者把各功能域拆成微服务。但当前项目没有多团队并行交付的压力，没有独立扩容前端的流量需求，也没有多服务独立发布的诉求。团队规模决定了：任何被拆出去的「额外架构层」都需要有人长期维护，而当前没有这个余量。

立即引入微服务或前后端分离会带来一串成本：

- 部署矩阵复杂化：多个容器、网关、反向代理、构建产物。
- 本地开发与调试成本上升：需要同时起多套服务。
- 跨服务数据一致性难题：分布式事务、消息队列、事件溯源。
- 在功能尚未定型时提前支付迁移成本，改一处需求要动多个仓库。

参考分析（docs/reference-analysis.md §5.3）对 MicroPyramid/django-crm 的研究印证：按业务域划分 app 的 Django 单体足以支撑 CRM 类系统，其「app 对应业务域」的切法值得借鉴。参考分析 §5.4 同时给出了反例：没有服务层、逻辑全堆在 model 与 signal 里的 DjangoCRM 不可取，这约束了模块化单体内「模块边界」的写法。

## Decision

采用模块化单体（Modular Monolith）架构：

- 整个系统是单个 Django 项目、单个进程、单个 PostgreSQL 数据库。
- 按业务域划分 app：accounts、customers、activities、documents、policies、claims、tasks、audit、core。
- app 之间只通过公开模型与明确函数边界交互，禁止跨 app 直接 import 内部实现细节；跨 app 逻辑放服务层函数而非互相贴 model 方法。
- 界面采用服务端渲染的 Django 模板加 HTMX、Alpine.js（见 ADR-007），不拆分独立前端。
- 第一版不做消息队列、独立网关、事件总线，也不预留半成品接口。

承认存在未来演进的可能：若某域（比如 documents 的缩略图管线）出现独立的资源需求，将以「先抽独立模块，再视情况独立部署」的方式演进。这是演进决策，不在当前范围提前支付。

## Consequences

正面：

- 单个容器即可部署，备份恢复简单，与 ADR-011 的备份方案天然契合。
- 所有业务逻辑共享一个数据库与事务边界，一致性维护成本低。
- 模块边界清晰，未来按域拆分有明确依据。

负面：

- 单点部署意味着单点故障，需要靠备份（ADR-011）与还原演练来弥补。
- 跨 app 的耦合要用代码规范和测试约束，防止退化成「大泥球」。
- 没有微服务的独立扩容能力，流量超出预期时需要整体评估。

## 被否决的备选

- 前后端分离 SPA：多一套构建链与接口层，与 ADR-007 的服务端模板决策冲突，团队无人长期维护前端工程。
- 微服务：无多团队、无独立扩容诉求，分布式一致性的成本在当前规模纯属浪费。
- 无边界的单体（一个 app 装所有模型）：模块不可测试、不可演进，违反参考分析「app 对应业务域」的结论。

## 实现要点

- app 依赖规则用 lint 检查约束（禁止 audit 之外的 app 反向依赖上层）。
- 每个 app 的 `services.py` 承载跨模型业务逻辑，视图只做编排。
- 单元测试按 app 组织，见 docs/testing.md。
